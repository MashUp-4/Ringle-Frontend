# Ringle — 튜터 탐색 경험 개선

> 나에게 맞는 튜터를 더 적은 화면 이동으로 비교하고 선택할 수 있도록.

CEOS 24기 MashUp 4팀의 프론트엔드 프로젝트입니다. 링글의 홈·튜터 탐색 흐름을 역기획하고, 디자인 시안과 실제 백엔드 API를 바탕으로 구현했습니다.

**[서비스 바로가기](https://ringle-frontend.vercel.app/)** · **[GitHub](https://github.com/MashUp-4/Ringle-Frontend)** · **[API 문서](https://ringle-backend.onrender.com/swagger-ui.html)**

---

## 01. 어떤 문제를 해결했나요?

튜터를 선택하려면 평점·후기·강점 등 여러 정보를 비교해야 합니다. 팀은 기존 탐색 과정에서 핵심 정보를 확인하기 위해 상세 화면을 반복해서 방문해야 하는 점을 문제로 정의했습니다.

이에 **홈에서 탐색을 시작하고, 목록 안에서 비교하고, 원하는 조건으로 후보를 좁히는 흐름**을 구성했습니다.

| 개선 방향               | 구현 내용                                                      |
| ----------------------- | -------------------------------------------------------------- |
| 홈에서 다음 행동 확인   | 예정 수업이 있으면 일정을, 없으면 학습 목적에 맞는 튜터를 표시 |
| 추천과 직접 탐색 구분   | 추천·전체 탭으로 탐색 목적에 맞는 진입점 제공                  |
| 목록에서 핵심 정보 비교 | 평점·리뷰 수·전공·학교 표시, 사진 hover 시 수락률·태그 제공    |
| 조건을 보며 후보 좁히기 | 좌측 아코디언 필터와 체크박스로 세부 조건 선택                 |
| 관심 있는 후보 모아보기 | 찜 저장·해제 및 찜한 튜터 목록 바로가기                        |

튜터 결정 시간과 탐색 피로를 줄이는 것이 목표이며, 효과에 대한 정량적 사용자 테스트는 진행하지 않았습니다.

## 02. 주요 화면

### 홈

- 회원 정보와 보유 수업권·포인트·쿠폰 조회
- 예정 수업 또는 맞춤 추천을 API 응답에 따라 표시
- 여러 예정 수업을 캐러셀로 탐색
- 학습 목적 변경 시 해당 카테고리의 튜터를 최대 2명 추천
- 추천 튜터 목록으로 이동

### 튜터 추천·전체

- 이름·전공 검색과 요일·시간대·강점·경험 등 복합 필터
- 카드에서 평가 정보 비교 및 hover 정보 확인
- 목록 데이터를 이용한 상세 팝업
- 검색·필터 조건을 URL에 반영하여 새로고침·뒤로 가기 시 유지

### 찜한 튜터

- 클릭 즉시 찜 상태 표시, 저장 실패 시 이전 상태 복원
- 저장 중 중복 요청 방지
- 홈과 목록에서 변경 상태 공유
- 저장 성공 안내에서 찜한 목록으로 이동

회원·홈·튜터 조회와 찜하기는 실제 API에 연결했습니다. 빈 응답이나 요청 실패를 목데이터로 대체하지 않습니다.

## 03. 기술과 설계

**React · TypeScript · Vite · Tailwind CSS · React Router · Fetch API · Vercel**

### API와 상태 관리

Fetch API 기반 공통 클라이언트에서 응답 처리·오류 분류·캐시·재시도를 담당합니다. 기능별 요청과 화면 데이터 변환은 컴포넌트에서 분리했습니다.

홈 응답은 `UPCOMING_CLASS`와 `RECOMMENDED_TUTORS`의 유니온 타입으로 구분합니다. 튜터 필터는 화면의 선택값을 서버 enum으로 변환하여 Query Parameter로 전달합니다.

| 상태                            | 관리 방식                             |
| ------------------------------- | ------------------------------------- |
| 모달·안내 메시지·아코디언       | 컴포넌트 내부 상태                    |
| 검색어·필터·찜한 목록 조회 조건 | URL 검색 파라미터                     |
| 회원·홈·튜터 조회 결과          | 조회 훅과 공통 API 캐시               |
| 찜 변경값·저장 중 상태          | `useSyncExternalStore` 기반 공유 상태 |

TanStack Query와 Zustand는 사용하지 않았습니다. 조회 상태는 React Hooks로 관리하고, 여러 화면에 영향을 주는 찜 변경은 공유 상태로 분리했습니다.

### 공통 UI와 구조

디자인 시안의 색상·타이포그래피·간격을 공통 토큰으로 정의하고 Tailwind와 CSS에서 사용합니다. 헤더·사이드바는 `AppShell`로 구성하며, 화면 너비에 따라 컬럼과 여백을 조정합니다.

```text
src/
├── assets/             # 이미지·아이콘
├── components/
│   ├── layout/         # 공통 레이아웃
│   └── ui/             # Modal, Icon, LoadingState
├── features/
│   ├── home/
│   ├── tutors/
│   └── user/           # 기능별 API·타입·훅·컴포넌트
├── hooks/              # 공통 훅
├── lib/                # API 클라이언트·사전 조회
└── pages/              # 라우트별 페이지
tests/                  # API·상태 처리 테스트
```

컴포넌트·타입은 PascalCase, 함수·변수는 camelCase, 커스텀 훅은 `use` 접두사를 사용합니다.

### 라우팅

| 경로                  | 화면                |
| --------------------- | ------------------- |
| `/`                   | 홈                  |
| `/tutors`             | 추천 튜터           |
| `/tutors/all`         | 전체 튜터           |
| `/tutors/all?saved=1` | 찜한 튜터           |
| `/tutors/:tutorId`    | 목록 기반 상세 팝업 |

## 04. 사용 흐름을 보완한 부분

| 상황                | 처리                              |
| ------------------- | --------------------------------- |
| 첫 조회             | 스켈레톤과 로딩 안내              |
| 결과 없음           | 빈 결과 안내                      |
| 요청 실패           | 오류 메시지와 재시도              |
| 장시간 대기         | 서버 연결 지연 안내               |
| 검색·필터 변경      | 250ms 입력 지연, 오래된 응답 무시 |
| 같은 조회 동시 실행 | 진행 중 요청 공유                 |
| 찜 저장 실패        | 상태 복원과 오류 안내             |

검색어는 최대 100자로 제한하고 앞뒤 공백을 제거합니다. URL 필터는 허용된 값만 사용하며, 중복값과 지원하지 않는 값은 요청에서 제외합니다.

화면 이동 시 대기를 줄이기 위해 성공 응답을 30초간 캐시합니다. 이후 최대 5분까지 최근 데이터를 먼저 표시하면서 갱신하고, 인접 화면 데이터를 미리 조회합니다. 찜 저장과 수동 재조회 시에는 캐시를 초기화합니다.

캐시가 없는 첫 조회와 서버 자체의 응답 지연은 남을 수 있습니다.

## 05. 협업

### 역할 분담

| 담당   | 주요 작업                                                                        |
| ------ | -------------------------------------------------------------------------------- |
| 최수민 | 홈·튜터 화면 구현 및 디자인 보정, 회원·튜터·찜하기 API 연동, 로딩 개선, 배포     |
| 백규민 | 튜터 필터와 URL 상태 관리, 홈 추천·예정 수업 API 연동, 카드·캐러셀·레이아웃 보정 |

디자인팀에는 배포 링크를 공유해 카드 hover·테두리·상단 메뉴·화면 배율을 검수받았습니다. 백엔드와는 Swagger와 필터 가이드를 기준으로 요청 파라미터와 응답 구조를 맞췄습니다.

### 작업 방식

```text
최신 dev 확인 → 기능 브랜치 → 구현·검증 → dev 대상 PR → 리뷰·머지
```

- npm과 `package-lock.json`으로 설치 기준을 통일하고 `npm ci`를 사용합니다.
- 브랜치는 `feat/`, `fix/` 등 작업 목적에 따라 구분합니다.
- 커밋 접두사는 `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`를 사용합니다.
- 변경을 기능별 PR로 나누고 구현 내용과 검증 결과를 기록합니다.
- Husky로 커밋 전 ESLint·Prettier 검사를 실행합니다.
- `dev`에 머지되면 Vercel 자동 배포가 시작됩니다.

## 06. 실행과 검증

```bash
git clone https://github.com/MashUp-4/Ringle-Frontend.git
cd Ringle-Frontend
npm ci
npm run dev
```

API 기본 경로는 `/backend`입니다. 별도 설정이 필요하면 `.env.example`을 참고하여 `.env.local`을 작성합니다.

```env
VITE_API_BASE_URL=/backend
```

로컬에서는 Vite 프록시, 배포 환경에서는 Vercel rewrite를 사용합니다. 백엔드 주소 변경 시 `vite.config.ts`와 `vercel.json`을 함께 확인해야 합니다. `VITE_` 환경변수에는 비밀값을 넣지 않습니다.

```bash
npm run lint
npm run format:check
npm run test:api
npm run build
```

작성 시점 기준 자동 테스트 28개로 필터 변환, 홈 응답 분기, 시간대 처리, 캐시·재시도, 사전 조회, 찜하기 상태 변경을 검증했습니다.

## 07. 현재 구현 범위

- 백엔드는 사용자 ID 1을 사용하며 로그인·인증·권한별 접근 제어는 구현되어 있지 않습니다.
- 실제 결제·예약 생성·일정 변경·예습은 구현하지 않았습니다.
- 튜터 상세 팝업은 목록 데이터를 사용하며 별도 상세 API는 연결하지 않았습니다.
- 일부 배너와 안내 콘텐츠는 정적 자료입니다.

폰트는 Pretendard Variable 1.3.9를 사용합니다. [공식 저장소](https://github.com/orioncactus/pretendard/tree/v1.3.9/packages/pretendard)가 출처이며, 라이선스는 `public/fonts/OFL.txt`에서 확인할 수 있습니다.

## 08. 개발 과정에서 겪은 문제와 해결

### 페이지마다 달랐던 화면 크기

각 화면을 통합하니 홈과 튜터 화면의 글자·카드 크기가 달라, 이동할 때 화면이 확대되거나 축소되는 것처럼 보였습니다. 공통 `AppShell`을 기준으로 배율과 레이아웃을 정리하고, 실제 서비스·디자인 시안과 비교하며 조정했습니다. 배포 링크를 활용한 디자인 검수로 상단 메뉴와 카드 표현도 보완했습니다.

### 목데이터와 실제 API 응답의 차이

실제 API를 연결하면서 추천 인원이 적거나 이미지·평점 등 일부 정보가 없는 경우를 처리해야 했습니다. 서버 응답을 화면 데이터로 변환하는 함수를 분리하고, 누락 정보의 표시 기준을 정했습니다. 빈 결과와 요청 실패를 구분하고, 부족한 추천 인원을 임의 데이터로 채우지 않았습니다. 필터는 백엔드 가이드에 맞춰 enum과 Query Parameter로 변환했습니다.

### 서버 응답 지연과 화면 전환 대기

첫 API 요청에 수십 초가 걸리거나 조회가 실패하는 상황이 발생했습니다. 서버 응답 시간과 프론트엔드 대기를 나누어 확인하고, 중복 요청 공유·응답 캐시·인접 화면 사전 조회를 적용했습니다. 첫 조회에는 스켈레톤을, 오래 기다리는 경우에는 지연 안내와 재시도를 제공했습니다. 서버 자체의 지연은 별도 확인이 필요한 부분으로 구분했습니다.

### 늦게 반응하던 찜하기와 상태 불일치

서버 저장 완료 후에만 아이콘을 바꾸어 클릭 반응이 늦게 보였고, 늦은 조회 응답이 변경된 찜 상태를 덮어쓸 가능성도 있었습니다. 클릭 즉시 상태를 반영하고 실패 시 이전 상태로 복원하도록 수정했습니다. 같은 튜터의 중복 요청을 막고, 서로 다른 튜터를 동시에 저장해도 실패한 항목만 복원되는지 테스트했습니다.

## 09. 느낀 점

문제점 도출과 요구사항 정의가 늦어지면서 와이어프레임과 디자인 작업도 함께 밀렸고, 개발과 검증을 촉박하게 진행하게 됐습니다. 앞 단계의 지연이 다음 역할의 작업 시간에도 영향을 준다는 점을 체감했습니다.

다음에는 핵심 문제와 필수 기능의 범위를 먼저 합의하고, 단계별 마감과 변경 사항을 팀 전체에 공유하고 싶습니다. 모든 내용을 확정할 때까지 기다리기보다 확정된 부분부터 병행할 수 있는 작업을 나누어, 개발과 검증 시간을 확보해야겠다고 느꼈습니다.
